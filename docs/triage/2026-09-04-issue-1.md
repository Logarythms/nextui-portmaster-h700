## Per-port detail

### Duke Nukem 3D — `PORTS-duke3d.txt`

Log evidence:
```
Initialized 192.0M cache
./rednukem(+0x6d858)
linux-vdso.so.1(__kernel_rt_sigreturn+0x0)
/usr/lib/aarch64-linux-gnu/libc.so.6(+0x998cc)
/usr/lib/aarch64-linux-gnu/libc.so.6(__strdup+0x14)
./rednukem(+0x5a660)
...
Initializing sound... Initializing sound:
Wrote rednukem.cfg
Wrote settings.cfg
```
The "Wrote … cfg" lines are the crash handler's shutdown path (stdout is pipe-buffered, so ordering vs. the stderr
backtrace is unreliable; the audio-init line ending in nothing is the real last step).

Chain, each link read from source:
1. NBlood `source/audiolib/src/driver_sdl.cpp` at the commit current for the Aug-2021 build
   (`03f8139`, line 225): `auto devname = Xstrdup(SDL_GetAudioDeviceName(0, 0));` — no NULL check. Same code in master today.
2. SDL 2.28.5 `src/audio/alsa/SDL_alsa_audio.c` `ALSA_HotplugIteration`: devices come only from
   `snd_device_name_hint(-1, "pcm", …)`; with no hints there are zero devices and `SDL_GetAudioDeviceName(0,0)` is NULL.
3. alsa-lib `src/control/namehint.c` `try_config`: a pcm node with **no `hint` sub-node is skipped** unless
   `defaults.namehint.showall` is true.
4. `assets/gt-asound.conf` (F47) is self-contained by design, defines `pcm.default`, `pcm.gt_stock_hooks`,
   `pcm.gt_stock_slave`, `ctl.hw`, has **no `hint` block and no `defaults` section**, and is applied via
   `ALSA_CONFIG_PATH` to **every port** not in the sleep blocklist (`build/build-pak.sh` ≈ line 906).

So since v0.4.0 every SDL port sees zero audio devices. Most ports open `NULL` (default) and never notice.
Anything in the EDuke32/NBlood family (Duke 3D, Redneck Rampage, Blood, PCExhumed, Ion Fury, EDuke32) crashes
at sound init. Pre-F47 (v0.3.x) the stock `alsa.conf` templates (`hw:`, `sysdefault:` with hints) were in
effect, so this is a regression, not a NextUI limitation.

Fix sketch (small):
```
pcm.default {
    type gt_suspend
    slave.pcm "gt_stock_slave"
    hint { show on  description "NextUI default output (sleep-safe)" }
}
```
SDL's prefix logic (`hw:`, `sysdefault:`, `default:`) matches nothing, then falls back to the device literally
named `default`, which it adds — exactly one device, non-NULL name. Add a grep assertion to `tests/test-22-port-sleep.sh`
(pcm.default carries a `hint {`), and ideally extend `tests/container-alsa-check.sh` to call `snd_device_name_hint`
against the templated conf so the enumeration is really tested. Device gate: Duke 3D shareware GRP on the RG SP.
Optional belt-and-braces: interpose `SDL_GetAudioDeviceName` in `gt-input-remap.so` to return `"default"` on NULL.

Unrelated noise in the same log: `sed: bad option in substitution expression` is the port's own
`sed -e "s/…/\1\"$GAMEDIR\/gamedata\"/"` with an unescaped path — fails on every CFW, harmless.

### Serious Sam TFE — `PORTS-serioussam.txt`

```
ERROR: ld.so: object '…/PORTS.pak/lib/gt-input-remap.so' from LD_PRELOAD cannot be preloaded (wrong ELF class: ELFCLASS64): ignored.
…/sstfe/Bin/ssam-tfe: error while loading shared libraries: libdl.so.2: wrong ELF class: ELFCLASS64
```
`port.json` → `"arch": ["armhf"]`; the launcher even exports `PORT_32BIT="Y"`. The 32-bit loader exists on the device
(`device_info.txt:208` tests `/lib/ld-linux-armhf.so.3` → `DEVICE_HAS_ARMHF="Y"`), but no 32-bit libc set is in its
search path, so the binary dies at the first library. Same wall F45 hit for Animal Crossing; F45 solved it per-port
with a pak-hosted 32-bit runtime.

Options: (a) force `DEVICE_HAS_ARMHF="N"` in `edit_portmaster_device_info` so harbourmaster hides/flags armhf-only
ports (small, honest); (b) later, generalize the F45 runtime: when a launcher exports `PORT_32BIT="Y"`, prepend the
pak's `libs.armhf` and preload `gt-input-remap.armhf.so` (feature-sized; the F45 runtime is SDL 2.0.12 + 15 libs, and
Serious Sam also needs 32-bit gl4es, which the port ships).

### Device profile — every log

```
gt-h700: input class sticks (js0 key word 1fff000000000000)
DEVICE_NAME=rg35xx-plus … ANALOG_STICKS=0
```
The key bitmap carries 313/316 (L3/R3 clicks) → the pak classified the pad as `sticks`, correctly: the RG35XX Pro ships
two hall-effect sticks (retailer and review pages agree). But the exact-SKU arm in the pin block
(`build/build-pak.sh` ≈ line 230) reads `rg35xxplus|rg35xxpro) gt_pm_device=rg35xx-plus`, and exact matches are never
refined by the input class (F53 design). Result: harbourmaster profile and `ANALOG_STICKS=0` say stickless, so ports pick
their stickless gptk/cfg (`fallout1.gptk.0`, Wolf3D `nosticks.cfg`) and analog-to-key synthesis has no analog lines to honor.

Fix: `rg35xxpro) gt_pm_device=rg35xx-h` (same 640×480 panel, 2 sticks; PortMaster has no dedicated rg35xx-pro profile
in 2026.07.28). Consider also: when an exact SKU says stickless but `GT_INPUT_CLASS=sticks`, log a warning or prefer the
stick sibling — the measured bitmap is ground truth for stick presence, the table is not.

### Wolf3D "blank screen" — ROOT CAUSE FOUND on the RG SP (2026-09-04 18:00)

Reproduced with the shareware entry: blank screen after selecting the game. Live inspection while stuck:

```
11910 ecwolf state=S wchan=n_tty_read      fd 0 -> /dev/console (= ttyS0)
gdb: #0 read () <- _IO_file_underflow <- scanf () <- ecwolf
```
`gdb -p PID -ex "call (int)fflush(0)"` pushed ECWolf's buffered stdout into `log.txt`:
```
IWad: Selecting base game data.
Please select a game wad (or 0 to exit):
1. Spear of Destiny Demo (*.SDM)
2. Wolfenstein 3D Shareware (*.WL1)
Which one?
```
ECWolf is waiting for a typed answer on the serial console. Mechanism, from `ECWolfEngine/ECWolf` master:

- `wl_main.cpp`: `--data <ext>` → `extension` → `IWad::SelectGame(files, extension, …)`.
- `wl_iwad.cpp:769-783`: the match is `basefiles[i].Extension.Compare(iwad)` — **case-sensitive** on Linux
  (`CompareNoCase` only under `ISCASEINSENSITIVE`, i.e. Windows/macOS). `Extension` comes from the on-disk
  filename, here `VSWAP.WL1` → `WL1`.
- The launcher passes `--data $(to_lower "$value")` = `wl1`, and its "lowercase every data file" loop is a no-op on
  FAT/exFAT (`mv AUDIOHED.WL1 audiohed.wl1` = same file). `WL1` ≠ `wl1` → no match → `I_PickIWad` → console picker.
- `wl_iwad_picker.cpp:321`: `if (scanf("%d", &i) != 1 || i > numwads) return numwads-1;` — with stdin = `/dev/null`
  (how other frontends launch ports) scanf fails instantly and the LAST data set is used, so the bug is invisible
  there. NextUI's launcher hands the port `/dev/console`, so scanf blocks forever → blank screen until Menu+Select.

The reporter's full game (`*.WL6`, uppercase from GOG) gives a 3-entry picker and the same hang.

Fixes: (pak, generic) run the port with `< /dev/null` in `run_port` — parity with every other CFW, and no port should
read the console on a handheld; (pak, port-fix, optional) rewrite the wolf3d launcher's `--data $(to_lower …)` to use
the real on-disk extension; (upstream) launcher should pass the actual extension case, or ECWolf should compare
case-insensitively everywhere. Unblocked live by injecting `2\n` with `TIOCSTI` on `/proc/<pid>/fd/0`: ECWolf then
mapped libEGL/libGLESv2/libmali and ran. Controls verdict: **all controls working and correctly mapped BOTH with and without the index remap** (Camille, RG SP, 18:05 and 18:15). So ECWolf needs NO allowlist entry: its `Joystick_*` config values are SDL GameController button enums (0 = A, 2 = X, 3 = Y, 5 = Guide, 6 = Start, 8 = RightStick, 11/12 = d-pad up/down, 4x = axes), not raw joystick indices — the earlier "raw-index class" reading in this doc was wrong. Wolf3D's only defect on NextUI is the console-picker hang above.

### Quakespasm segfault — ROOT CAUSE FOUND on the RG SP (2026-09-04 18:20)

Reproduced with the shareware `pak0.pak`, launcher wrapped in `gdb -batch -ex run -ex bt`:
```
Thread 1 "quakespasm.aarc" received signal SIGSEGV
#0  0x0000000000000000 in ?? ()
#1  MALI_GLES_SwapWindow (_this=…, window=…) at /tmp/sdl2-h700/src/video/mali-fbdev/SDL_maliopengles.c:73
#2  SDL_GL_SwapWindow () from …/PORTS.pak/lib/gt-input-remap.so     ← our interposer, passes through to the real swap
#3  quakespasm main loop
```
Disassembly of NextUI's SDL fork (`lib/libSDL2-2.0.so.0`, ships debug info) resolved with `ptype`/offset queries:
line 64 calls `_this->egl_data->eglCreateSyncKHR` (offset 264), line 73 calls `_this->egl_data->eglDestroySyncKHR`
(offset 272) **unguarded**. SDL loads these via `eglGetProcAddress` on whatever `SDL_VIDEO_EGL_DRIVER` names.

The port (like every gl4es PortMaster port, via `libgl_default.txt` → `LIBGL_FB=2` → the launcher's
`export SDL_VIDEO_EGL_DRIVER="$GAMEDIR/gl4es.aarch64/libEGL.so.1"`) points SDL at gl4es's **fake EGL stub**:
- Quakespasm's stub (older gl4es, 26,568 B): exports `eglCreateSyncKHR`, `eglClientWaitSyncKHR`, **no `eglDestroySyncKHR`**,
  and its `eglGetProcAddress` returns NULL for unknown names → line 64 succeeds, line 73 calls 0 → SIGSEGV.
- Jedi Outcast's stub (newer gl4es, 37,624 B): exports `eglDestroySyncKHR` and also a catch-all `eglStub` for unknown
  names → the same swap path is harmless → JO runs.
- The real Mali EGL (`/usr/lib/libmali.so.0`) exports the whole KHR sync family.

So this is a NextUI SDL fork bug (unguarded optional EGL extension pointer in the mali-fbdev swap) exposed by any port
bundling a pre-`eglDestroySyncKHR` gl4es fake EGL. It is independent of the pak (our shim only forwards the swap) and
of the launcher version; the reporter's older launcher hit the same line.

Fix candidates: (pak, generic) neutralize `SDL_VIDEO_EGL_DRIVER` exports in port launchers at patch time so SDL
always loads the real Mali EGL while gl4es stays the GL driver — **experiments run (18:25–18:35):**
- `unset SDL_VIDEO_EGL_DRIVER` (real Mali EGL, gl4es libGL only): still crashes, but elsewhere — `SDL_CreateWindow` fails
  and the fork's cleanup `MALI_EGL_DeinitPixmapSurfaces` (`SDL_malivideo.c:396`) calls an uninitialized function pointer
  (`ldr x1,[x21,#56]; blr x1`). So the gl4es fake EGL is load-bearing for these ports (it translates the desktop-GL
  context request into GLES), and it is a second unguarded pointer in the fork's error path. **Bypass is not a fix.**
- `SDL_VIDEO_EGL_DRIVER=/tmp/jo-libEGL.so.1` (Jedi Outcast's newer gl4es fake EGL, 37,624 B, exports

  "$GAMEDIR"/gl4es*/libEGL.so.1` at launch, rewrite the launcher's `SDL_VIDEO_EGL_DRIVER=` export). Build the stub from
  ptitSeb/gl4es (MIT) in the docker lane rather than borrowing JO's; version-mixing with the port's libGL worked here. (upstream NextUI) guard the

### Keyboard delivery on NextUI — mechanism found (2026-09-04 18:40)

While Quakespasm ran with its documented controls, the question arose whether gptokeyb's keyboard reaches SDL after all.
It does not: the port's shipped `id1/config.cfg` sets `joy_enable "1"` and binds the pad natively identically to its
gptk (`LSHOULDER +jump`, `RSHOULDER +attack`, `ABUTTON impulse 10`, `BBUTTON impulse 12`, triggers quicksave/load), so the
launcher's `+joy_enable 0` is overridden and Quakespasm is a **native SDL_GameController port** here — playable as-is
once the EGL stub is fixed.

Controlled check with BYTEPATH (shim off via `files/gt-remap-ports.txt`, LÖVE 11.5 runtime, keyboard-event menus):
dead, and still dead with a 1.5 s wait after gptokeyb started (so NOT a startup race). Live inspection of the game:
gptokeyb's uinput device exists (`N: Name="Fake Keyboard"`, `H: sysrq kbd event3`); the game holds `/dev/input/event1`
(pad, twice) and an inotify watch on `/dev/input` (SDL's joystick hotplug fallback) — **never `event3`**. The SDL fork's
strings contain `SDL_EVDEV_DEVICES` and `SDL_EVDEV_Init`: that is upstream SDL's **no-libudev** keyboard/mouse path, which
adds only the devices named in the env var `SDL_EVDEV_DEVICES` ("class:path,…", class = SDL_UDEV bits: 1 mouse, 2
keyboard) and otherwise `/* TODO: Scan the devices manually, like a caveman */`. Nothing on NextUI sets it → SDL never
opens any keyboard or mouse → gptokeyb's output is dead. This is the precise reason behind the pak's F26/F31 synthesis.

**EXPERIMENT PASSED (18:50).** ROM-dir BYTEPATH launcher, shim OFF: after gptokeyb starts, `sleep 1.5`, resolve the
"Fake Keyboard" node from a `/proc/bus/input/devices` copy, `export SDL_EVDEV_DEVICES="2:/dev/input/$gt_ev"` → the
launcher log shows `SDL_EVDEV_DEVICES=2:/dev/input/event3` and **BYTEPATH's keyboard-driven menu works through
gptokeyb's real virtual keyboard**, no synthesis. Console keyboard mode (`KDGKBMODE` on tty0/tty1) is K_UNICODE after exit
— no side effect observed.

Consequences: NextUI-h700 CAN deliver gptokeyb's keyboard (and, by the same SDL code path, its mouse — REL events go
through `SDL_EVDEV_Poll` for any listed device) to ports. The pak's F26/F31 key synthesis exists only because SDL's
no-udev evdev layer was never told about the device. Generic implementation sketch ("gptokeyb passthrough"): in
`gt-input-remap.so`, interpose `SDL_Init`/`SDL_InitSubSystem`; when a `gptokeyb` process exists (scan `/proc/*/comm`) and
`SDL_EVDEV_DEVICES` is unset, wait ≤2 s (poll a `/proc/bus/input/devices` snapshot) for the "Fake Keyboard" node, set
`SDL_EVDEV_DEVICES="3:/dev/input/eventN"` (keyboard|mouse) and call the real init. Then: disable key synthesis when the
passthrough is active (double input otherwise), keep synthesis as the fallback for ports without gptokeyb (Sonic F43
overlay, Animal Crossing F45 evdev path), and re-check the LD_PRELOAD-overwriting launchers (Doom Engines `hacksdl.so`:
the shim never loads there — append instead of replace at launcher patch time). **Gameplay verified too (18:58):** BYTEPATH ship movement (keyboard *polling*, the F31 case) works — SDL's own keystate
updates from the real device; the game held `/dev/input/event3` open (`SDL_EVDEV_DEVICES=2:/dev/input/event3` in its env).
gptokeyb's uinput device advertises `EV=7`, `REL=3` even for a keyboard-only gptk, i.e. it is always a keyboard+mouse
device — list it with class 3. Still open: mouse delivery on a mouse-driven port (OpenTTD is free; the RG SP has no
sticks, so use a d-pad→mouse gptk), and Jedi Outcast/FreeSerf on the reporter's device.
